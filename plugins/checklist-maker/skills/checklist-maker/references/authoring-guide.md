# 手順書の中身の書き方

スキーマに合っていても、中身が悪ければ手順書として使えない。ここは
**「何を書くか」**のガイド。形式は `data-format.md` を見ること。

---

## 1. まず構造を決める（フェーズ → 手順）

`sections` = フェーズ、`items` = 手順。**工程で切る**のが基本。

```
① 準備   … 作業前に揃えるもの・確認すること
② 実施   … 本体の作業
③ 確認   … 結果の検証・記録・後始末
```

CheckListMaker 自身の実例（`docs/templates/exe作成手順.checklist.json`）も同じ形:

```
① 準備：Node.js（無料）を入れる
② 材料をそろえる
③ 組み立てる
…
```

- **フェーズ名は丸数字＋コロン＋目的**（`① 準備：Node.js（無料）を入れる`）にすると
  目次と Word の見出しがそのまま読める
- 1フェーズあたりの手順は **3〜8個** を目安に。10を超えるならフェーズを割る
- 「異常時の対応」「中止する条件」は独立したフェーズにする

## 2. 手順（item）の書き方

### `text` — 1手順1動作

- **動詞で終える**。「〜を開く」「〜を確認する」「〜を入力して Enter を押す」
- 主語（誰が）は書かない。対象と動作だけ
- 2つの動作を「〜し、〜する」で繋がない。分ける
- 番号は書かない（アプリが自動で振る）

| ✗ | ○ |
|---|---|
| `設定について` | `設定画面を開く` |
| `nodejs.org を開いてダウンロードする` | `ブラウザで nodejs.org を開く` ／ `LTS 版をダウンロードする` |
| `1. 電源ON` | `電源ボタンを押して起動する` |

### `note` — 「なぜ」と用語補足

読み手が初めてでも詰まらないように。実例:

```
"note": "アドレス欄に「nodejs.org」と入力して Enter。　※Node.js＝.exe を組み立てて動かすための無料の土台ソフト。"
```

- 判断の分岐（「〜なら中止する」）
- 専門用語の1行説明（`※〜＝〜`）
- 場所の補足（「3階の分電盤」）

### `body` — 詳細・表・選択肢

設定値が複数あるとき、条件で分岐するときは表にする。
使えるタグは20種の allowlist だけ（`data-format.md` 参照）。

```html
<table><thead><tr><th>状態</th><th>判断</th></tr></thead>
<tbody><tr><td>成功</td><td>次へ進む</td></tr>
<tr><td>失敗</td><td><strong>中止</strong>して再取得を依頼する</td></tr></tbody></table>
```

### `time` — 標準時間（分）

- 半角数字の**文字列**（`"5"`）。アプリの入力候補は 1〜60 分
- 入れるとフェーズ見出し・Word・Excel に合計が出る。**所要時間の見積りが要る手順書では必ず入れる**
- 分からないものは空文字 `""` にする。**推測で埋めない**

## 3. 並び順

**重要なことから先に**。とくに:

- 中止条件・安全上の注意は、その作業の**手前**の手順に置く（事後では意味がない）
- フェーズ内では実行順。実行順に意味がないなら、失敗すると影響が大きいものから

## 4. 画像の扱い

**AI は画像を作らない。`"images": []` のまま出す。**

CheckListMaker の本領は「操作しながら自動でスクリーンショットを撮る」録画機能なので、
画像は次の流れでユーザーが入れる:

1. CheckListMaker を起動し、AI が作ったデータを取り込む
2. 上部バーの **「キャプチャ撮影」** を押して、実際に対象の操作をひととおり行う
   （クリックのたびに画面が自動保存される）
3. 録画を止めると取り込みウィザードが開くので、既存フェーズに差し込む
4. すでに手元に画像がそろっているなら、上部バーの **「画像インポート」** から
   フォルダを選び、**1枚＝1手順**としてまとめて取り込む
5. 1枚だけ差したいときは各手順の **「🖼 画像」** から貼る

ユーザーへの案内文にこの流れを1〜2行で添えること。

> 手元に本物の画像ファイルがあり、確実に埋め込みたい場合だけ dataURL を使う。
> その場合はサイズに注意（画像込みで数MBに達しやすい）。

## 5. 表紙（coverPage）を付けるか

- **社内の正式文書として配るなら付ける。** `preset: "doc-header"` で文書番号・版数・
  作成者が枠に出る。`revisions` に初版を1行入れておく
- 手元のチェックリスト用途なら `enabled: false` か `coverPage` 自体を省略
- `date` は **ISO `yyyy-mm-dd`**。日付をでっち上げず、分からなければ空文字にしてユーザーに聞く

## 6. 素材から手順書を起こすときの手順

別プロジェクトで「この作業の手順書を作って」と言われたときの進め方:

1. **素材を集める** — README、`docs/` の spec、CI 設定、`package.json` の scripts、
   これまでの会話。実際に動くコマンドが書いてあるものを優先する
2. **工程に分ける** — 準備／実施／確認。素材に無い工程を想像で足さない
3. **各手順を1動作に割る** — コマンドは `body` に、実行の意味は `note` に
4. **分からないところは空にして、ユーザーに質問する** —
   所要時間・担当者・文書番号・日付は推測で埋めない
5. **検証する** — `node scripts/validate-checklist.mjs <file>`
6. **渡し方を案内する** — `export-and-limits.md` の取り込み手順をそのまま伝える

## 7. やってはいけないこと

- 素材に無い手順を「たぶんこうだろう」で書く
- `time` や `date` や `docNumber` を埋めるために値をでっち上げる
- 存在しない画像の base64 を作る
- `type` を `"todo"` にする（`note`/`time`/`body` が出力から消える）
- `body` に `<img>` や `<a>` や見出しタグを書く（サニタイズで消える）
- 1つのファイルに無関係な複数の手順書を詰め込む（更新も受け渡しも追いにくくなる。
  1ファイル＝1手順書にする）
