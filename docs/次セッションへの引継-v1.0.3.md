## 2. 最優先の不具合 — サムネイルのD&Dコピーが完全に不動作

**重大度: blocker ／ 確認済み（実機で再現・修正案も実測で検証済み）**

### 何が起きているか

サムネイル（`.thumb`）を別の手順へドラッグしても `dragstart` が一度も発火せず、
画像はコピーされません。必ず画像エディタが開きます。`f298819` で入れた
`copyItemImage` / `attachImageDnD` 一式と `docs/spec-dnd-image-copy-phase-move.md` が
**丸ごと死にコード**になっています。

サムネイルの `title` は「クリックで編集／**別の手順へドラッグでコピー**」と表示しているので、
ユーザーには使える機能として見えています。

### 原因

`document` レベルの `pointerdown` 委譲ハンドラが、allowlist に載せた
`data-action="edit-image"`（＝サムネイル自身）に対して `e.preventDefault()` を呼んでいます。
Chromium では信頼できる `pointerdown` の `preventDefault()` が**互換 `mousedown` ごと抑止**し、
ネイティブ D&D が開始できません。

実測（ブラウザ実入力）:

| 押した対象 | 発火したイベント |
| --- | --- |
| `.step-text` | `pointerdown` → `mousedown` ✓ |
| `.thumb` | `pointerdown` のみ。**`mousedown` が来ない**。画像エディタが即座に開く |

### 直し方

**`preventDefault` を外すだけでは直りません。** 押下と同時にモーダルが開くため、
ドラッグを始める余地がありません（実測で確認済み）。`edit-image` を `pointerdown` から
`click` へ移してください。

1. `pointerdown` 委譲ハンドラの allowlist から `'edit-image'` を外す
2. 同ハンドラの `else if (action === 'edit-image')` 分岐を削除する
3. 既存の `click` 委譲の `switch(action)` に `case 'edit-image':` を足し、
   `openImageEditor(c, sectionId, itemId, Number(btn.dataset.index))` を呼ぶ
   （`click` 側は現在 `index` を読んでいないので取得を追加する）

`pointerdown` 方式を残したい場合の代替は、押下時は blur による確定だけ行い、
`openImageEditor` は `click`（または移動が閾値未満だった `pointerup`）まで遅らせる形です。

### 検証

- 手動: 画像付き手順のサムネイルを別の手順へ D&D → コピー先に増え、コピー元にも残る。
  単純クリックでは従来どおりエディタが開く。手順テキストを編集中（未確定）のまま
  サムネイルをクリックしても、テキストが確定しつつエディタが開く
- 自動: Electron 31 ＋ CDP（`Input.setInterceptDrags` → `dispatchMouseEvent` →
  `dispatchDragEvent`）で D&D を再現し、images 枚数が `[1,0]` → `[1,1]` になること、
  `document.querySelector('.modal.img-editor')` が `null` のままであることを確認

### 併せて入れるべきもの

- **回帰テスト**（major）。この不具合は「純関数 `copyItemImage` は正しいが DOM の配線が
  別機能に潰されている」型で、既存テストでは原理的に検出できません。`test/` 配下 24 ファイルを
  grep しても `attachImageDnD` / `dragstart` / `dragover` / `drop` に触れるテストは **0 件**です。
  jsdom（`test/harness.js` の `bootApp`）で2本足してください。
  - (a) `.thumb` に `PointerEvent('pointerdown', {cancelable:true})` を dispatch し、
    `evt.defaultPrevented === false` を assert（ネイティブ D&D の開始条件を代理で守る）
  - (b) `.thumb` に `dragstart`、コピー先 `.item` に `dragover` / `drop` を、`dataTransfer` を
    簡易スタブにして dispatch し、コピー先の `images` が1枚増え、コピー元が減らないことを assert
  - **修正前の `index.html` に当てると両方落ちること**まで確認する
- **Electron のファイル画像モード（`img:` 参照）での検証**（minor）。今回の実測はブラウザ単体モード
  （`images` が dataURL 実体）でした。参照共有の経路は未通過です。修正後に `npm start` で、
  D&D コピー前後で `userData/data/images` のファイル数が増えないこと、コピー元の手順を削除して
  再起動してもコピー先の画像が生きていることを確認してください
- **仕様書に因果を書き残す**（minor）。`docs/spec-dnd-image-copy-phase-move.md` に
  「`pointerdown` の `preventDefault` と `draggable` 要素は同居できない」ことを明記する。
  この allowlist は機能追加のたびに action が増えており（`edit-image` → `move-item-up/down`
  → `merge-item-up`）、同じ壊れ方を再発させやすい構造です

## 3. `main` に入った PR #46 由来の不具合（5件）

**PR #46 のレビューで確定し、マージ後の `main`（`ccfe809`）でも 5件すべてそのまま成立します。**
うち2件（3-2, 3-5）は `main` のコードを実際に走らせて再現を確認済みです。
本ブランチの改修とは別物ですが、いま `main` に載っている実害なので、担当を決めてください。

### 着手順序（依存があります）

1. **3-5 を最初に**。これを直さないと 3-2 のバリデータ強化が「本当に落ちるか」検証できない
2. 次に **3-2**（`json-to-html.mjs` と `validate-checklist.mjs`）
3. そのあと `index.html` を **3-1 → 3-3 → 3-4** の順で。
   **3-1 と 3-3 は同じ取り込みハンドラを書き換えるうえ、複数件取り込みは壊れたデータが
   混ざる機会を増やすので、必ず同一改修で入れること**

### 3-1. 取り込み用 HTML の2件目以降が無警告で消える（blocker）

`plugins/checklist-maker/skills/checklist-maker/scripts/json-to-html.mjs` は
`state.checklists` を**全件** `clm-data` に埋め、全件描画し、CLI も「チェックリスト N 件」と
報告します。しかし `index.html` の `parseChecklistFromHtml` は `data.checklists[0]` しか読みません。

2件入りを渡すと、バリデータは「✓ 問題なし」、`json-to-html` は「2 件」、しかし取り込まれるのは
1件目だけで、2件目以降は無警告で消え、アプリは**1件目のタイトルで成功を報告**します。
SKILL.md は「既存 JSON に手順書を追記する」を ✅ に挙げ、README・`export-and-limits.md`・
`data-format.md` の3か所が HTML を既定の受け渡し形式として推しているため、
**既定経路がそのまま成果物消失**になります。追記した成果物は配列の末尾なので、
いちばん失われやすいのが「いま作ったもの」です。

最小の直し: `json-to-html.mjs` で `checklists.length > 1` のときにエラー（または明示的な警告＋
1件目のみ出力）にする。docs に「HTML は1チェックリストのみ。複数件は JSON ＋『追加・更新する』」を追記。

### 3-2. 生成 HTML が無エスケープ・無サニタイズ（major）

`json-to-html.mjs` の `renderCover` / `renderChecklist` が表紙テキストと `body` をそのまま
流し込みます。アプリ側は必ず `sanitizeBodyHtml` を通して属性を全て捨てますが、生成 HTML には
その防御がありません。さらに `validate-checklist.mjs` の `tagsIn` は**タグ名しか見ない**ので、
`<span onmouseover="...">` は「✓ 問題なし」で通ります。`coverPage.title` に `<script>` を
入れると警告どまりで、しかも文面が「許可されていないタグは削除されます」と**この経路では嘘**です。

### 3-3. 形状不正なデータを取り込むとアプリが起動不能になる（major）

`mergeChecklistsInto` に形状検証がなく、`sections` 欠落データを取り込むと
`Store.commit` の順序（mutator → persist → notify）により**不正データが先に localStorage へ
書かれ**、その後 `renderHome` が throw します。インポートボタンは `renderHome` の出力の中に
しかないため、リロードしても復旧できません。

### 3-4. 取り込みが保存の成否を見ずに成功トーストを出す（major）

`store.lastSaveOk` を見ていません。このリポジトリには録画ウィザードと `commitImage` に
`lastSaveOk === false` なら `undo()` ＋ `notifySaveError(..., {force:true})` という
確立した書き方があります。画像入りをまとめて取り込む JSON マージは容量上限を踏む代表例です。

### 3-5. バリデータのテストが構造上けっして失敗しない（major）

`test/aiskill.test.js` の `runValidator` は stdout しか返しませんが、バリデータはエラーを
`console.error`（stderr）に出します。したがって `assert.doesNotMatch(out, /エラー/)` は
**原理的に常に真**です。ほか3か所も同様でした。`runValidator` を stdout / stderr 別々に返す形にする。

## 4. 本ブランチ自身の積み残し

v1.0.3 で入れた改修（ToDo 画像の原寸表示 ／ Ctrl コピーのドラッグ中追従 ／ Shift の水平垂直拘束）
そのものに残っている弱点です。

### 4-1. `renderImages` の第3引数 `large` が常に `true`（major・要仕様判断）

呼び出しは `renderItem` と `renderStep` の2か所だけで、**どちらもリテラル `true`** です。
`is-large` を付け外しする JS も存在しません。結果として基底の

```css
.thumb { height: 56px; max-width: 120px; object-fit: cover; }
```

は4プロパティすべてが `.item-images.is-large .thumb` に上書きされ、**死にコード**になっています。
分岐しない引数と一度も適用されない CSS が同居している状態です。

- 案A: `large` 引数を廃止し `.item-images` に統合、`.thumb` の該当4行を削除してセレクタを平坦化
- 案B: 「小さく表示」トグルを新設して `large=false` の呼び出し元を実際に作る

**着手前にユーザーへ確認してください。** ToDo に大きな画像が並ぶとリストが極端に縦長になる副作用も
あり、案B の余地があります。どちらにせよ「常に true の引数」は残さないこと。

### 4-2. `onKey` の `objDrag` ガードが広すぎる（minor に格下げ）

`if (objDrag && ev.key !== 'Escape') return;` の `objDrag` は `pointerdown` の瞬間に非 null に
なるため、**しきい値未満の「押しただけ・動かしていない」状態でも** Delete と履歴操作が死にます。
守る対象（掴んでいる実体が `objects` 差し替えで迷子になる）は `moved` 後にしか存在しないので、
`if (objDrag && objDrag.moved && ev.key !== 'Escape') return;` に狭めるのが妥当です。

> **注記**: 調査時に「`pointerup` を取りこぼすと復帰不能になる」という重い主張がありましたが、
> 反証担当が**否定**しました。`canvas.addEventListener('pointerup', finish)` と `finish` 内の
> `if (objDrag) { objDrag = null; ... }` があるため、`pointerup` が来れば解除されます。
> 残るのは「`moved` 前でも効いてしまう」という範囲の話だけなので minor です。

### 4-3. ドラッグ中の Escape の意味が未定義（major）

Escape だけガードを素通りする設計にした結果、ドラッグ中の Escape の挙動を決めないまま
既存の「選択解除 → 閉じる」ラダーへ流れています。

- 1回目: `selectedId` を null にするだけで `objDrag` は生きたまま。**図形は掴まれ続けマウスに追従**
  （選択枠だけ消える）。Ctrl コピー中なら複製も残る
- 2回目: `selectedId` が既に null なので `close()` に到達し、**ドラッグ途中でエディタが閉じて
  未保存の注釈がすべて失われる**

Office では Escape はドラッグの取り消しです。`onKey` の Escape 分岐の先頭に1段追加してください。

```js
if (objDrag) {
  if (objDrag.moved) { setDragCopy(objDrag, false); applyObjDrag(objDrag, { x: objDrag.sx, y: objDrag.sy }); }
  objDrag = null; canvas.style.cursor = ''; recomposite(); return;
}
```

差分0で `orig` へ完全復帰する性質は `test/imageeditor.test.js` の
「掴んだ位置を渡すと開始状態へ戻る」で既に担保済みです。決めた挙動は spec 8章に明記すること。

### 4-4. Shift 拘束の意味が新規描画と食い違う（major・要仕様判断）

`move`（図形全体の平行移動）では「移動量を水平・垂直に倒す」＝期待どおりですが、
`p1` / `p2` / `tip` / `pt*` では**掴んだ点の移動量だけ**を倒すので、線が水平・垂直になりません。

例: `(0,0)-(10,10)` の線の `p2` を Shift で右へ引くと `y2` は 10 のまま残り、
**斜めの線が斜めのまま横に伸びます**。

ユーザーが期待するのは「Shift＋端点＝もう一方の端点を基準に 0°/45°/90° へスナップ」
（＝新規描画時の `shapeFromDrag` と同じ）です。spec 8章は「引くときは45°、後から動かすと水平垂直」
という差を『残す』と書いていますが、実際に残っているのは **揃う／揃わない** の差です。

推奨: 端点系だけ拘束の基準をアンカー点に変える（`p1` なら `s.x2/s.y2`、`p2` なら `s.x1/s.y1`、
`pt*` なら隣接頂点）。`dragConstrains` を「移動量拘束（`move` / `tip`）」と
「アンカー基準スナップ（`p1` / `p2` / `pt*`）」の2種類に分ければ、引くときも動かすときも
同じ45°ルールになり、spec 8章の『差は残す』という記述自体を削除できます。
`tip`（吹き出しの尻尾）はアンカーが無いので移動量拘束のままでよい。

### 4-5. 右クリック削除メニューが `objDrag` 中でも開く（minor）

`onKey` で「ドラッグ中は Delete を受け付けない」と塞いだのに、まったく同じ
`deleteSelectedObject` を呼ぶ `contextmenu` 側は無防備です。`objDrag` 中は `drawing` が false
なので素通りし、しかも `selectedId = hit.id` でカーソル直下の図形へ選択を付け替えます。
左ボタンを押したまま右クリックはこのアプリの公式ジェスチャ（要望10・要望14）なので踏みやすい。
`contextmenu` ハンドラの先頭に `if (objDrag) return;` を足してください。

### 4-6. 修飾キー追従がテストで守られていない（minor）

今回の改修の中核である Ctrl / Shift の追従に回帰テストがありません。

- `dragConstrains` は `applyObjDrag` と同じスコープ（クロージャ外）にいるのに
  `window.__test__` の公開リストに載っていません。**1行足すだけで公開できます**
- `setDragCopy` は `objects` と `selectedId` を直接触る副作用関数なので jsdom から呼べません。
  純粋な部分を `nextDragCopyState(d, on) → { action: 'clone'|'revert'|'none' }` として
  切り出せば、状態遷移（`mode !== 'move'` は不可、`moved` 前は不可、同値なら none、
  on→off→on で元へ戻る）をテストできます
- `syncDragMods` の変化検出も `modsChanged(d, {ctrl, shift})` として純化できます

### 4-7. ドキュメントと実装のずれ（minor）

`docs/spec-image-editor-enhancements.md` 8章（Escape の挙動・右クリック削除の扱い・要望エントリ）と
`docs/インストールと使い方ガイド.md` の但し書きを、4-3 / 4-4 / 4-5 の結論に合わせて更新すること。
